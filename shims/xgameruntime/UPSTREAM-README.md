# xgr: xgameruntime stand-in

`idl_table.py` + `gen_stub.py` build a typed interface table from IDL files and generate `xgameruntime.dll` source from it (not committed: the IDLs are LGPL, from the Xodus project).
Two builds, from an x64 VS prompt in this directory:

```
python -I idl_table.py <xodus>/include table.json
python -I gen_stub.py table.json gen
:: logging stub only (every method logs its first call and fails)
cl /nologo /LD /O2 /EHsc /std:c++17 gen\xgr_stub.cpp /Fe:xgameruntime.dll /link /DEF:gen\xgameruntime.def
:: with the runtime: XTaskQueue/XAsync and system info (vendored from GrandTheftXbox, MIT, runtime\GTX_LICENSE.txt) plus an offline local user (runtime\impl_user.cpp)
cl /nologo /LD /O2 /EHsc /std:c++20 /DXGR_WITH_RUNTIME /I runtime gen\xgr_stub.cpp runtime\xtask.cpp runtime\impl.cpp runtime\impl_user.cpp runtime\impl_storage.cpp runtime\impl_package.cpp runtime\impl_save.cpp runtime\impl_system.cpp runtime\impl_network.cpp runtime\impl_streaming.cpp runtime\impl_accessibility.cpp runtime\impl_capture.cpp runtime\impl_misc.cpp runtime\impl_store.cpp runtime\impl_launch.cpp runtime\impl_ui.cpp runtime\impl_handles.cpp runtime\gtx\gtx_log.cpp /Fe:xgameruntime.dll /link /DEF:gen\xgameruntime.def shell32.lib ole32.lib
cl /nologo /EHsc test_client.cpp
cl /nologo /EHsc /std:c++20 test_user.cpp
cl /nologo /EHsc /std:c++20 test_package.cpp
cl /nologo /EHsc /std:c++20 test_save.cpp
cl /nologo /EHsc /std:c++20 test_system.cpp
cl /nologo /EHsc /std:c++20 test_store.cpp
cl /nologo /EHsc /std:c++20 test_ui.cpp
cl /nologo /EHsc /std:c++20 test_launch.cpp advapi32.lib
```

Environment: `XGR_LOG=<file>` (interfaces queried, first call of each stubbed method, unknown interface ids), `GTX_LOG=<file>` (the vendored layer), `XGR_GAMERTAG`, `XGR_USER_ID`, `XGR_PLS_DIR` (persistent local storage directory; default `PersistentLocalStorage` next to the executable), `XGR_PLS_SIZE_MB` (its quota; default the `SizeMB` of `MicrosoftGame.Config` next to the executable), `XGR_PACKAGE_ID`, `XGR_PACKAGE_STORE_ID`, `XGR_PACKAGE_DISPLAY_NAME`, `XGR_PACKAGE_PUBLISHER`, `XGR_PACKAGE_DESCRIPTION`, `XGR_PACKAGE_VERSION`, `XGR_TITLE_ID` (package identity when `MicrosoftGame.config` does not give it; otherwise synthetic), `XGR_SAVE_ROOT` (game saves; default `%LOCALAPPDATA%\xgr\saves`, then `<user id>\<service configuration id>`). There is no locale override: `XPackageGetUserLocale` reads the Windows user settings (below).
`test_client.cpp` reaches the DLL the way the GDK's static library does (`QueryApiImpl` + vtable slots): it adds the local user through the async framework, reads id, state and a privilege,
and the system analytics info (reports Windows.Xbox / Xbox Series X). Implemented: the whole XAsync/XTaskQueue layer, XThread hints, system and title ids, and the user functions with no network (XUserAdd*, ids, gamertag, state, age group, privileges, change-event registration, sign-out deferral (E_GAMEUSER_DEFERRAL_NOT_AVAILABLE outside a sign-out), device association, the desktop answers for the default audio endpoint and controller lookup), and persistent local storage (path, path size, space info: a directory limited to the title's declared quota), and XPackage for a title that is one fully installed package in the executable's directory (identity, enumeration, chunk and feature queries, install monitors, mounting the main package, write statistics; `test_package.cpp` checks it). Anything needing a store or a download returns the documented error. Every XGameSave and XGameSaveFiles function is local-only storage (`runtime\impl_save.cpp`): each container is a folder of blob files plus a manifest replaced in one rename, so a failed or abandoned update keeps the previous contents; titles' container and blob names never become file names. Nothing syncs (`needsSync` is always false), the quota is the documented 256 MB per user and configuration id, and `XGameSaveFilesGetFolderWithUi` shows no UI. `test_save.cpp` checks them; run it, then `test_save.exe reopen` to check that saves survive a new process.
Everything else logs and fails: game UI that needs a window, network queries, closed captions, speech.
`runtime/impl_system.cpp` (tested by `test_system.cpp`) adds the startup-facing system calls with honest offline answers: app-specific device id (the documented all-zero id), download-bandwidth hint, display timeout deferrals (a Windows display-required power request), the HDR state of the primary desktop output (read through DXGI), error callback and options (the exported `XErrorReport` calls the stored callback and, unless it returns false, writes a debugger string when the options ask for one; it never breaks or fast-fails),
feature availability (derived from the override table), activation/protocol/invite registrations that never fire, an offline connectivity hint (stack initialised, no connectivity, initial notification as documented), the PC answers for networking configuration and statistics, high-contrast mode from Windows, and the headless game UI (dialogs, pickers and text entry complete with E_ABORT unless the title set UI callbacks; no window is ever shown).
Vendored files (`runtime/xtask.*`, `xgr_internal.h`, `impl.cpp`, `gtx/`) are GrandTheftXbox's; `impl.cpp` has one local change, marked in the file.

Behaviour of the implemented methods where the console is not matched exactly (written from the interface signatures and the public GDK documentation):
* Persistent local storage (`runtime/impl_storage.cpp`): a directory, `XGR_PLS_DIR` or `PersistentLocalStorage` next to the executable, created on first use; the path ends in a backslash like the console's `T:\`.
  Quota: `XGR_PLS_SIZE_MB` or the `SizeMB` of `MicrosoftGame.Config`; a title that declares none gets `E_NOTIMPL` (the console's answer is not known).
  Space info: total = quota, used = size of the files under the directory, total free = quota - used, available = that limited by the PC volume's free space (no cluster or metadata accounting).
  `PromptUserForSpaceAsync/Result` show no prompt: the request completes with `E_ABORT`, the documented result when the user does not free space (a null async block gets `E_INVALIDARG`; no other result is documented).
  `XPersistentLocalStorageMountForPackage` (in `runtime/impl_package.cpp`, tested by `test_package.cpp`): the only title is this one, so its own package identifier gets a package mount handle whose path is this storage directory (read and closed with the `XPackage` mount calls); any other identifier, or a title that declares no quota, gets `HRESULT_FROM_WIN32(ERROR_FILE_NOT_FOUND)`, the documented answer when the storage does not exist. Whether the console lets a title mount its own storage this way, and whether it requires the shareable flag in `MicrosoftGame.config` for that, is not documented; the flag is not read.
* `XUserGetGamertag`: `XGR_GAMERTAG` or `Player`; Classic is cut to 15 bytes; the offline profile has no modern suffix, so ModernSuffix is empty and UniqueModern equals Modern.
* A buffer shorter than the text plus its terminator gets `HRESULT_FROM_WIN32(ERROR_INSUFFICIENT_BUFFER)`; the `XUserGetGamertag` page names `E_INSUFFICIENT_BUFFER` for this case without giving its value.
* `XUserIsStoreUser`: true, the documented console answer ("always returns true on console"); on PC it is false when nobody is signed in to the Store or the Store account differs from the XUser. This is a stand-in answer, not measured on a title: a title that acts on it and goes to the Store gets the offline XStore answers (`E_GAMESTORE_NETWORK_ERROR`). `XUserGetMaxUsers`: 4, a choice (no GDK page gives a number). `XUserRegisterForChangeEvent` rejects a null callback or token with `E_INVALIDARG`, like the device and audio registrations (the page marks both as required and names no code); no change event ever fires. `test_user.cpp` pins these.
* `XPackageIsPackagedProcess` (`runtime/impl_package.cpp`): true, as for a console title. `XPackageGetUserLocale`: the user's locales are the Windows default locale followed by the preferred Windows UI languages. The first of them that `MicrosoftGame.Config` lists under `Resources` (case-insensitive) is returned; failing that, the first of them whose primary subtag matches a listed language (the user's locale is returned, not the listed one). With no listed language the call succeeds with an empty string, as the function page prescribes. When languages are listed and none is close, it returns `HRESULT_FROM_WIN32(ERROR_NOT_FOUND)`, a local choice: no page names a code for that case. The console's matching rules (script subtags, regional fallbacks) are not verified.
* Chunk selectors (`runtime/impl_package.cpp`, tested by `test_package.cpp`): a Language selector may list several languages separated by semicolons, and `{Lang "en-US;fr-FR"}` is treated as `{Lang en-US},{Lang fr-FR}` (documented). Each language must be one the package lists, case-insensitively, or the call returns `E_GAMEPACKAGE_INVALID_SELECTOR`; an empty item (`"en-US;"`) is refused the same way and spaces are not trimmed (both local choices). A package that lists no languages accepts every Language selector. There is no `layout.xml` to resolve against, so Tag and Feature selectors are never invalid, only null text is refused.
* `XPackageUninstallUWPInstance`: always `E_NOTIMPL`, the answer the function page permits on platforms without the API; nothing is uninstalled.
* Networking (`runtime/impl_network.cpp`, tested by `test_network.cpp`): the preferred local UDP multiplayer port is the documented default, 3074, from the blocking, async and change-notification variants; registering for changes sends the documented initial notification and nothing after it. Security information for a URL is per-title configuration fetched from Xbox services, so after checking that the URL is well-formed https the query completes with `HRESULT_FROM_WIN32(ERROR_NETWORK_UNREACHABLE)`. `XNetworkingVerifyServerCertificate` checks its arguments and then fails closed with `E_NOTIMPL`. No connection is made.
* `runtime/impl.cpp` (vendored) also registers `impl_storage.cpp`'s and `impl_package.cpp`'s overrides, next to `impl_user.cpp`'s.
* The offline user has no Xbox network identity, so nothing is invented for it: `XUserGetTokenAndSignature(Utf16)Async` and `XUserGetMsaTokenSilentlyAsync` complete with `E_GAMEUSER_FAILED_TO_GET_TOKEN` and their ResultSize/Result calls return that error; `XUserGetGamerPictureAsync` completes with `HRESULT_FROM_WIN32(ERROR_NOT_FOUND)` (no picture; no XUser page documents a code for this case).
  `XUserResolvePrivilegeWithUiAsync` succeeds without UI, matching `XUserCheckPrivilege` (every privilege granted); `XUserResolveIssueWithUi(Utf16)Async` completes with `E_ABORT` like the headless game UI; `XUserAddByIdWithUiAsync` adds the local user for its own id and returns `E_GAMEUSER_USER_NOT_FOUND` for any other.
  `XUserSignOutAsync` completes with `E_NOTIMPL` and the user stays signed in (`XUserIsSignOutPresent` is false here). The remote-connect and SPOP handlers (documented for Steam Deck) are stored and never called; `XUserPlatformRemoteConnectCancelPrompt` and `XUserPlatformSpopPromptComplete` return `E_INVALIDARG` because no prompt is ever active.
  These calls reject a null async block or out pointer, a handle that is not the local user and unknown option bits with `E_INVALIDARG`.
* Game streaming (`runtime/impl_streaming.cpp`, tested by `test_streaming.cpp`): a title that runs locally and is never streamed. `XGameStreamingInitialize`/`Uninitialize` track the init state and every HRESULT call outside it returns `E_GAMESTREAMING_NOT_INITIALIZED`. `IsStreaming` is false and no client is ever connected, so per-client queries return `E_GAMESTREAMING_CLIENT_NOT_CONNECTED`, gamepad-reading queries `E_GAMESTREAMING_NOT_STREAMING_CONTROLLER`, and the server location `E_GAMESTREAMING_NO_DATACENTER` with a name size of 0. Connection-state registrations are accepted and never fire; touch layout requests do nothing; `XGameStreamingSetResolution` accepts only 1280x720 and 1920x1080.
* Accessibility (`runtime/impl_accessibility.cpp`, tested by `test_accessibility.cpp`): `XClosedCaptionGetProperties` reports the user's Windows closed-caption settings (colours, edge effect, font style, size as FontScale), read through Windows.Media.ClosedCaptioning, and reports captions as enabled only after the title calls `XClosedCaptionSetEnabled(true)`. The speech-to-text calls validate their arguments and drop the text, because there is no system overlay. The speech synthesizer reports no installed voices, `XSpeechSynthesizerCreate` fails with `E_NOTIMPL`, every handle-based call returns `HRESULT_FROM_WIN32(ERROR_NOT_FOUND)`, and `XGameRuntimeIsFeatureAvailable` reports XSpeechSynthesizer as unavailable; no audio is produced.
* App capture (`runtime/impl_capture.cpp`, tested by `test_capture.cpp`): a machine with no capture or broadcast service; nothing reads the screen, records, or writes a media file. `XAppCaptureEnableRecord`/`DisableRecord` are remembered; video capture settings report captures by games as not allowed, so `XAppCaptureRecordTimespan` returns the documented `E_ACCESSDENIED`, and screenshot, diagnostic and user-recording calls return XAppCapture error codes. Metadata events and states are accepted and dropped (documented when nothing is capturing) and remaining metadata storage is 0. `XAppBroadcastShowUI` shows no UI (`E_ABORT`); the broadcasting-changed and metadata-purged registrations never fire. `XAppCaptureTakeScreenshot` clears the result and returns the same refusal as the other captures (blocked by title after `XAppCaptureDisableRecord`, otherwise disabled by the capture setting); `XGameRuntimeIsFeatureAvailable` reports XAppCapture as unavailable because nothing can be captured.
* `XTaskQueueIsEmpty` (in `runtime/xtask.cpp`, tested by `test_misc.cpp`) answers from the queue itself: each port counts its callbacks from submission until they return, so a port reads non-empty while work is queued, delayed, running, or cancelled but not yet delivered. `XGameEventWrite` (`runtime/impl_misc.cpp`) checks its required arguments and accepts the event without sending or storing it. `XGameActivationAcceptPendingInvite` and `XGameInviteAcceptPendingInvite` return `E_INVALIDARG` for a null or empty URI and otherwise `HRESULT_FROM_WIN32(ERROR_NOT_FOUND)`: the activation and invite registrations never fire offline, so no invite is ever pending (no code is documented for that case).
* XStore (`runtime/impl_store.cpp`, tested by `test_store.cpp`): a PC with a cached licence for the running game and no connection to the Store. Contexts are created with or without a user (the documented PC behaviour). The game licence is active, full and permanent, with SKU `<store id>/0010` (the SKU id is a choice); there are no add-on licences. The title's own package can be licensed (`XStoreAcquireLicenseForPackage`), and `XStoreQueryPackageIdentifier` maps its store id to its package identifier; any other package is not owned (`LM_E_CONTENT_NOT_OWNED`), and any other store id has no installed package (the documented `E_INVALIDARG`). Everything that needs the Store service fails with `E_GAMESTORE_NETWORK_ERROR`: entitlement queries (the GDK documents them as needing a connection) and product queries (they read the Store catalogue; their reference pages do not say), `XStoreCanAcquireLicenseFor*` (documented as needing a connection, so it answers the same for the title's own package as for any other), durables, consumables, collections and purchase ids, licence tokens (an empty `customDeveloperString` is `E_INVALIDARG`, documented), package updates and downloads, and the purchase, review, redeem, gifting and product-page UIs. No product query handle is ever returned, so enumerating one is `E_INVALIDARG` and it has no more pages; nothing is purchasable. Licence-changed and licence-lost registrations never fire.
* Handle tracking (`runtime/impl_handles.cpp`, tested by `test_misc.cpp`): the calls that hand out task queue, user, display timeout deferral, game save provider, container and update, package installation monitor, package mount, store context and store licence handles report them, so `XSystemIsHandleValid` is true from the first reference handed to the title until its last close, and the `XSystemHandleTrack` callback gets Created and Destroyed at those two points (duplicating a handle that returns the same pointer, as `XTaskQueueDuplicateHandle` and `XUserDuplicateHandle` do, adds a reference and no event). The callback runs synchronously on the thread that created or closed the handle; a null callback turns it off, and handles stay tracked for `XSystemIsHandleValid`. `UninitializeApiImpl` (`XGameRuntimeUninitialize`) reports each handle still open through `XErrorReport` with `E_FAIL` and a message naming its type; the code and text are not documented. Not done: handles passed into other calls are not validated (an invalid handle is not reported through `XErrorReport`), and the text entry handle of the open text entry pull request does not report yet. The speech synthesizer, screenshot stream, sign-out deferral and store product query handles are never created here.
* Launching (`runtime/impl_launch.cpp`, tested by `test_launch.cpp`): `XLaunchUri` drops a leading `ms-bgm-` (the documented PC behaviour) and opens the URI with `ShellExecuteExW`, waiting until the shell has launched it, so Windows shows its own prompt when no app handles the scheme. It returns `E_INVALIDARG` for text without a scheme of at least two characters (so a drive path such as `C:\game.exe` is never run) or that is not UTF-8, and `E_ACCESSDENIED` for `file:` URIs; both refusals are local choices. The requesting user is ignored. `XLaunchNewGame` starts the executable (relative paths resolve against the current directory) with the given arguments and the caller's current directory, then ends the calling process with `TerminateProcess` and exit code 0, also when the new game could not be started (documented). Both processes exist for a moment, so the one-executable-at-a-time guarantee holds only once the caller has exited; DLC is not unmounted and the default user is ignored (there is one local user). `XLaunchRestartOnCrash` rejects a non-zero `reserved` with `E_INVALIDARG` and registers the arguments with `RegisterApplicationRestart` for crashes only (no restart for hangs, updates or reboots); Windows restarts only a process that crashed after running for at least 60 seconds, through Windows Error Reporting, and the console's devkit-only `E_NOTIMPL` does not apply on PC.
* Game UI drawn by the title (`runtime/impl_ui.cpp`, tested by `test_ui.cpp`): after `XGameUiSetUiCallbacks`, each of the message dialog, error dialog, player picker, profile card, send-invite, achievements and text entry calls whose callback is set calls it on its async block's queue (the process queue for a block without one) when the async work runs, with a callback handle, copies of the call's strings and arrays, and the title's context; the call stays pending until the matching `XGameUiSet*UiResponse`, whose values the Result calls then return. `useSystemUiIfAvailable` makes no difference because no system UI exists here. A null `callbacks` pointer clears them; a null member leaves that UI headless (`E_ABORT`). A response call returns `E_INVALIDARG` for a handle that no callback was given, that belongs to another kind of UI, that was already answered or whose call was canceled; `XAsyncCancel` ends a pending call with `E_ABORT`. `XGameUiShowTextEntryResultSize` counts the terminator of the title's text; the response is not checked against `maxTextLength`, and the player picker response is not checked against the selection limits. `XGameUiSetMultiplayerActivityGameInviteUiResponse` refuses every handle until the multiplayer activity invite UI (in an open pull request) routes to its callback.
  `XGameUiShowWebAuthentication(WithOptions)Async` check the user, an `https` request URI, the completion URI and the options (PreferFullscreen is ignored on PC, documented), then complete with `E_ABORT` like the other headless UI: no web view is shown and nothing is fetched. ResultSize and Result return that error and leave the result pointer null.
* `XPackageUninstallChunks` (`runtime/impl_package.cpp`, tested by `test_package.cpp`): the one installed package needs every chunk to run, so after checking the package and selectors (a chunk-id-only selector is `E_INVALIDARG`, documented; an empty list is `E_INVALIDARG`, a local choice) it removes nothing, returns `S_OK`, and the chunks keep reporting Ready. No file is deleted.
