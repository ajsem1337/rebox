# D3D12.X interfaces and unified memory

This page records what the console DLLs in `../xsx` show about D3D12.X, and the plan built on it.
Every claim cites an address in a binary. Re-check any of them with
`nix run .#d3d12x-probe -- dis <dll> <address>`. Once the exe is dumped, rerun the same
analysis on it, because the exe will exercise far more of the API than these DLLs do.

Sources:

- `XboxBvhBuilder.dll` (BVH): its exports carry mangled parameter types (`ID3D12Device11*`,
  `ID3D12GraphicsCommandList4/6/8*`), so the object behind every vtable call is known.
- `amd_fidelityfx_upscaler_xbox.dll` (FFX): device calls identified by their IID argument and
  argument shape.

```sh
nix run .#d3d12x-probe -- slots ../xsx/XboxBvhBuilder.dll   # typed slots + direct field accesses
nix run .#d3d12x-probe -- iids ../xsx/*.dll                 # GUIDs and the vtable slot they feed
```

### Other projects (checked 2026-11-21)

- [AnyBox](https://github.com/Dark3581/AnyBox) (GPLv2) relinks a title's imports onto its own DLLs.
  Its `d3d12_x` and `xmem` are still parameterless stubs, so it has no D3D12.X facts yet.
- [Xbox2Windows](https://github.com/R0Y00/Xbox2Windows) (MIT) does static-recompilation experiments
  on a the target title Scarlett build. That build has the same bundled DLLs as `../xsx` and no main
  executable. Its `docs/experiments.md` supports the root-signature flags `0x03000000` and the
  XMem call shapes we use. It also confirms log2(alignment) in XALLOC bits 24–28 for two callers:
  Bink `0x05e50000` → 32 bytes, AMD `0xa8004000` → 256.

### Cross-check: ScarlettX

[ScarlettX](https://github.com/Freminet/ScarlettX) (`src/shims/d3d12_xs_shim.cpp`, commit bda18b4)
is an HLE that runs a retail Unity title (Concept Destruction) through its own Xbox COM proxies.
Its slot tables were traced from that title. **Everything that overlaps agrees with the
findings below:** device slots 0–41 are PC, command-list slots ≥ 28 are PC + 4, and the
command list's inline fast paths use `+0x18`/`+0x30`. The two sources cover different
slots, so the tables below merge them, with ScarlettX-only rows marked **SX**. The repo has
no licence file, so take facts from it but don't copy its code.

The two projects target different stacks. ScarlettX loads the PE itself and runs on Windows
D3D12; its Vulkan backend and unified memory are both at 0%. It returns host GPU VAs for
buffers and copies guest memory into textures. That doesn't satisfy the
`XMemVirtualQuery(gpu_va)` check below, so the identity-mapping plan still stands.

## IIDs: same as PC

Both DLLs pass the **PC D3D12 IIDs**, byte for byte, to the device methods that take them:
`ID3D12Resource`, `ID3D12DescriptorHeap`, `ID3D12RootSignature`, `ID3D12CommandSignature`,
`ID3D12PipelineState`, `ID3D12Heap`, `ID3D12RootSignatureDeserializer`, and `ID3D12Device`
(QueryInterface, FFX 0x18000de66). Neither DLL references an IID that isn't in the mingw
headers. Any Xbox-only interfaces (`ID3D12DeviceX`-style) and the IID the exe passes to
`D3D12XboxCreateDevice` are still unknown.

## Inline fast paths: title code writes into our objects

This is the critical finding. D3D12.X headers inline the hot command-list methods, so title code
reads and writes **fields of the command-list object** and only calls the vtable when a buffer
is full. From BVH 0x180020ea0, which inlines SetPipelineState, SetComputeRootSRV,
SetComputeRoot32BitConstant and Dispatch:

| Field | Use |
|---|---|
| `+0x18` | write cursor (a `BYTE*`) |
| `+0x28` | limit for a 16-byte Dispatch record |
| `+0x30` | limit for other records; at or past it, call the vtable method instead |
| `+0x140` | "root arguments dirty" byte |
| `+0x141` | copied from PSO flags bit 20 |
| `+0x143` | checked before choosing the Dispatch header |
| `+0x344 + 4*i` | per-root-parameter record header (one dword each) |
| `+0x544`..`+0x563` | copy of the bound PSO's 32-byte record |

PSO objects are read too: `pso+0x10` (a 28-byte record copied into the stream) and `pso+0x20`
(flags).

The records the title appends:

- **SetPipelineState**: the 28 bytes from `pso+0x10`.
- **Root SRV/CBV/UAV**: `hdr[i]` + 64-bit GPU VA (12 bytes). Root constant: `hdr[i]` + value
  (8 bytes). If `hdr[i] & 0xC0000000` is zero, the title also sets `+0x140`.
- **Dispatch**: `0x4002C400` if `+0x140` or `+0x143` is set, else `(0x1000BA00 | flag141) << 2`, then `x, 1, 1`
  (16 bytes). Then it clears `+0x140`.

What this means for the design:

1. **We can't hand out vkd3d-proton's command lists.** The title would write records over
   vkd3d's internal state. `d3d12_xs` has to allocate its own command-list objects.
2. **The simple way to handle the fast paths is to disable them** (ScarlettX's approach). Keep
   0x1000 zeroed bytes after the vtable pointer, so cursor == both limits == 0. Every inline
   path then sees a full buffer and calls the vtable method. That holds for every check in BVH
   0x180020ea0, including Dispatch's `+0x28`. The unconditional writes (`+0x140`, `+0x544`)
   land in the zeroed block. The cost is one indirect call per command, which is fine to start
   with.
3. **Decoding the records is a later optimisation.** The per-root-parameter headers and the PSO
   record come from objects we create, so we could pick tags that are easy to decode. The title
   hardcodes only the op headers it inlines (Dispatch above; Draw* and others are in the exe).
4. **The device has inline paths too** (XValkyrie, `docs/research/d3d12x.md` and `gdk-titles.md`,
   from an Xbox One title and confirmed on Series; neither of our DLLs or ScarlettX's title showed
   it). A flags byte at device +0x18 says whether `CreateConstantBufferView` (17) and
   `CopyDescriptorsSimple` (24) must be called. When it's zero the title writes the CBV's V#
   itself (address | `0x0010000000000000`, then size/16 | `0x0002403C00000000`; a null one is
   `0x0002403C00000001`) and copies CBV_SRV_UAV/RTV/DSV descriptors as memory, 16 bytes at a
   time. +0x10 holds a null-buffer address. The device proxy sets the byte to 1 (the smoke test
   checks it). A title compiled without the check still writes inline, and our CPU handles are
   vkd3d-proton's, so that would corrupt its heaps: handing out handles into console-format
   memory is the eventual fix.

## Layouts depend on the title's SDK

ScarlettX (1e5473d, 2026-11-22, from the method names in each SDK's debug driver and a title's
calls) found that `D3D12XBOX_CREATE_DEVICE_PARAMETERS.Version`, the first u32 of the creation
parameters, picks the vtable layouts. Titles built against 0x20001 get the tables above. From
0x20004 on:

- **Command list**: two methods were added at 59 and 60, and every named method from 61 on is the
  0x20001 one two slots later (CopyTextureRegionX moves from 83 to 85).
- **Queue**: two methods were added ahead of Signal: Signal is 16 and PresentX 32 (14 and 30
  before).

`D3D12XboxCreateDevice` logs the parameters (version, debug flags, ring size, scratch sizes,
prefer-WARP) and creates queues with the later layout from 0x20004. Slots 11-15 trap there,
because where the two methods went isn't known. The smoke test signals a fence through slot 16.

Command lists follow the version too. Read with XValkyrie's 0x20001-era table (June 2020 kit:
56-59 PC 56-59, 69-90 console memory writes and waits, 83 CopyTextureRegionX, 105-121 PC 60-76),
everything the target title's own DLLs call fits the later layout: FSR's ExecuteIndirect at 61 (PC 59 plus
two), the BVH builder's write/wait calls at 71, 73 and 90 (69, 71 and 88 plus two), and 141-148
past the end of the older table. So from 0x20004 lists get a table built that way: 0-55 as
before, 56-58 the PIX markers, 59-60 trapping, 61 ExecuteIndirect, 85 CopyTextureRegionX,
107-123 PC 60-76 (render passes, raytracing), 126/127 shading rate, 129 DispatchMesh, 146 Barrier,
148 the embedded allocator. Titles passing an older version keep the mixed table below. The
smoke test records markers and a forwarded PC method on such a list and executes it.

## Texture tiling

the target title's texture pools store textures in two Gfx10 swizzle modes. bcpack-rs measured the BC1
block order on the retail pools: `xyxxyyxyxyxyx` in 64 KiB tiles and `xyyxxyxyx` in 4 KiB tiles
(element x/y bits from the lowest address bit). Rendered from AMD addrlib's swizzle tables (Mesa,
MIT), those are exactly `SW_64KB_D` and `SW_4KB_S` for 8-byte elements: the modes without pipe
or bank XOR. addrlib, created as Navi21 (family `FAMILY_NV`, external revision 0x29,
`gb_addr_config` 0x444), gives the same mip chains as bcpack-rs's measured layout: total size,
first mip in the tail and every level's offset, for 256x256x9, 1024x512x11, 64x64x7,
2048x2048x12 and 300x200x9 in both modes, unchanged with another pipe count. So addrlib can
detile what the title has in memory, given the swizzle mode. Which console resource-desc
`Layout` value selects which mode is still unknown (SCARAB only names
`D3D12CONS_TEXTURE_LAYOUT_SWIZZLE_MODE_64KB_R_X`).

Leonida's census of the pools' ETPF descriptors agrees: tile mode `(mode >> 1) & 0xF` 0 is
`SW_64KB_D`, 1-3 `SW_4KB_S` (9-12 cubemaps), and every texture whose mip 0 is 1 MiB or more uses
the 64 KiB mode. `title_textures.c` uses that split until the console layout's meaning is known:
placed textures are registered with their address, detiled into their own memory at creation and
after DirectStorage writes to them, and the layout of each is logged.

## Root signature flags

Console root signatures may carry Xbox-only flag bits: 0x01000000 (`FORCE_MEMORY_BASED_ABI`
according to xbox-emulator, unverified), 0x02000000 and 0x80000000. Leonida measured that
Microsoft's PC `D3D12CreateRootSignatureDeserializer` rejects them. vkd3d-proton doesn't: it
serializes and deserializes them unchanged, and root signature creation only logs a FIXME and
ignores them. The smoke test (`test_xbox_root_flags`) checks all three, so nothing strips them.
What the bits mean for the console's SGPR layout is still unknown.

## Unified memory: GPU VA == CPU VA

Evidence that console titles treat GPU virtual addresses as CPU pointers:

- BVH 0x180019c69: a `D3D12_GPU_VIRTUAL_ADDRESS` from the build desc goes straight into
  `XMemVirtualQuery` as a CPU address. The code then requires `State == MEM_COMMIT`,
  `Protect & (READONLY|READWRITE)`, and `(info+0x30) & 3`, a GPU-access field after the
  `MEMORY_BASIC_INFORMATION`.
- Command-list slot 148 returns a CPU pointer that the title fills and then binds as a root SRV
  address (0x180020ed6 → 0x180020f80).
- FFX copies shader bytes into `XMemAlloc` memory and passes that pointer in a PSO desc
  (0x18000565d).

`XMemVirtualQuery` is `(HANDLE process, const void *address, info*)` with a 0x40-byte info
struct. The shim used VirtualQuery's argument order, which would have written the struct over
the queried memory. Fixed in `shims/xmem/xmem.c`, with a smoke-test check.

### Getting identity mappings out of Vulkan

vkd3d-proton derives every GPU VA from `vkGetBufferDeviceAddress`, so we need buffers whose
device address equals the CPU address the title already holds. `tests/gpuva_probe.c` (native
Linux, `make build/gpuva_probe`) tries these routes:

| Route | How | lavapipe (here) | RADV 26.x, Radeon 890M |
|---|---|---|---|
| import | `VK_EXT_external_memory_host` on the xmem range, plus capture/replay with `opaqueCaptureAddress = ptr` | identity (llvmpipe uses host pointers) | **no**: memory is shared, but the requested address is silently ignored; got `0xffff800100200000` |
| placed | allocate, read the BDA, map at that CPU address with `VK_EXT_map_memory_placed` | extension missing | **no**: the BDA is in the GPU's upper half (`0xffff8…`), which is kernel space on the CPU |
| replay-low | ordinary allocation with `opaqueCaptureAddress = base`, then a placed map at `base` | skipped | stock: **refused** (`VK_ERROR_INVALID_OPAQUE_CAPTURE_ADDRESS`); **`.#radv-rebox`: IDENTITY OK**, device address `0x200000000000` as requested, GPU writes visible at the same CPU address |
| replay-high | as replay-low but requesting `base \| 0xffff800000000000`, mapped at `base` | skipped | **works**: device address granted exactly as requested, placed CPU map at `base`, GPU writes visible there |

So RADV allocates device addresses from the upper half of the 48-bit GPU address space, and
doesn't apply replay addresses to imported host memory. What's left:

Stock RADV rules out identity: replay-low is refused. The offset route (replay-high) works but
doesn't fit the console model. Titles store one address and use it from both sides:
BVH hands GPU VAs to `XMemVirtualQuery`, and ScarlettX's title writes texels through
`GetGPUVirtualAddress`. Meanwhile the GPU loads addresses from memory (BVH nodes, bindless
tables, ExecuteIndirect arguments). No single form of an offset address satisfies both.

### Patched RADV

The refusal is RADV policy, not hardware or kernel. `radv_amdgpu_bo.c` passes
`AMDGPU_VA_RANGE_HIGH` on every VA allocation. libdrm's `amdgpu_va_range_alloc2` then uses its
upper-half manager, which can't satisfy a lower-half `va_base_required`. Without the flag,
libdrm uses its lower-half manager (from 4 GiB to `virtual_address_max`) and honours the
required base. Importing host memory (`buffer_from_ptr`) never passes a replay address at
all, which is why the import route silently ignored ours.

`patches/mesa-radv-low-va-replay.patch` drops `AMDGPU_VA_RANGE_HIGH` only when the replay
address is non-zero, below 2^47, and the allocation isn't 32-bit. Ordinary allocations and
genuine capture/replay (always upper half) are unchanged. RADV's other upper-half assumption,
`address32_hi`, applies only to its 32-bit allocations (shaders, descriptors), which still go
to the upper half. The flake builds it as `.#radv-rebox` (Mesa 26.3.1, RADV + lavapipe only).

```sh
nix build .#radv-rebox
VK_ICD_FILENAMES=$PWD/result/share/vulkan/icd.d/radeon_icd.x86_64.json build/gpuva_probe
```

Verified 2026-11-21 on a Radeon 890M (RADV STRIX1, `.#radv-rebox`): `replay-low: IDENTITY OK`.
So the design is: xmem reserves a CPU window and backs
GPU-visible allocations with Vulkan memory requested at the matching device address, mapped at
that same CPU address. vkd3d-proton needs a hook to create heaps at a given address. Wine
also needs to know about the placed mapping (winevulkan already uses placed maps for WoW64).

## Runtime implementation

### Identity memory

How GPU-visible memory ends up at the same GPU and CPU address:

1. **xmem.dll** reserves `REBOX_GPUVA_WINDOW` (default 1 TiB at `0x200000000000`) at load,
   so Wine never hands that range out.
2. **xmem** sends GPU-visible memory types (`memory_type != 0`) to **d3d12_xs**'s
   `ReboxGpuAlloc`. It falls back to `VirtualAlloc` if d3d12_xs is unavailable, if
   `REBOX_GPU_MEMORY=0` is set, or under the loader lock.
3. **`ReboxGpuAlloc`** (`gpu_memory.c`) suballocates 64 MiB custom heaps (`WRITE_BACK`, `L0`)
   on the one device the title also gets from `D3D12XboxCreateDevice`. Each heap is spanned by a
   UAV buffer and mapped. vkd3d-proton therefore knows every byte as a resource and resolves raw
   VAs into it. `XMemVirtualQuery` and `XMemFree` consult its table.
4. **`VK_LAYER_REBOX_gpuva_identity`** (`layers/gpuva_identity.c`, host side, under
   winevulkan):
   - On `vkCreateDevice` it enables `bufferDeviceAddressCaptureReplay` and
     `VK_EXT_map_memory_placed`.
   - Every host-visible `vkAllocateMemory` gets a capture/replay device address from a window
     allocator.
   - `vkMapMemory` maps that memory at the same CPU address.
   - Unmaps are deferred to `vkFreeMemory`, which leaves the range reserved.
   - Because whole allocations are identity-mapped, vkd3d-proton's suballocations are too.
   - If the driver refuses the address (stock RADV), the layer logs once and passes
     allocations through.
5. **`rebox-run`** loads the layer and, on AMD GPUs, points `VK_ICD_FILENAMES` at
   `.#radv-rebox`.

RADV behaviours the layer works around (all seen on the 890M, confirmed in the Mesa source):

- **Guard page:** on GPUs with the SMEM out-of-bounds erratum, `radv_bo_create` maps one extra
  page past each allocation (`RADEON_FLAG_VM_PAD_1PAGE`). The window leaves a gap after every
  allocation.
- **Lazy VA release:** a freed allocation's GPU VA range isn't released at once, so reusing it
  straight away is refused. The window allocator is next-fit and only reuses ranges after
  wrapping around. On a refusal for a memory type that has worked before, it skips 256 MiB and
  retries.
- **32-bit memory types:** RADV has separate memory types for 32-bit-addressable memory
  (descriptor buffers, device-generated commands; `memory_types_32bit`). The Mesa patch
  leaves those in their own range, so their first refusal marks the type as never-identity
  and later allocations of it pass straight through. Titles don't reach that memory by
  pointer.

Verified 2026-11-21 on a Radeon 890M with `.#radv-rebox`: inside Wine, every `ReboxGpuAlloc`
heap is identity-mapped (first chunk at `0x200000000000`), including heaps allocated right after
a free. The only refused type is the 32-bit one.

`d3d12_xs` logs whether the first heap is identity-mapped. The device proxy also creates
DEFAULT-heap buffers, and DEFAULT heaps that hold only buffers, as custom `WRITE_BACK`/`L0`
heaps (slots 27, 28 and 76). vkd3d-proton keeps those mapped, so the layer identity-maps them as
well. On an APU that memory is system RAM either way. Textures and mixed heaps keep ordinary
upper-half GPU VAs; texture GPU VAs get scratch memory (below).

### Xbox texture layouts

`D3D12_RESOURCE_DESC.Layout` values from 0x100 up are console tilings. 0x101 is the FidelityFX
recurrent texture's, per Xbox2Windows. Every path that takes a resource desc maps them to
`D3D12_TEXTURE_LAYOUT_UNKNOWN`, the driver's choice, and logs each value once. That covers device
slots 25, 27, 29, 30, 38 and 76. The layout only matters to titles that address texels in memory
themselves, which get scratch GPU VAs (below).

### Proxies

`shims/d3d12_xs/proxy.c` implements the device, queue, graphics and copy command lists, and
descriptor heaps:

- **PC-compatible slots** go through a generated thunk: load the wrapped object from `+0x1000`,
  then jump to its PC slot. Argument lists don't need to be known.
- **Slots that differ** get C implementations:
  - device: 8, 12, 14, 43, 48, 62, 68, 69, 73, 76, 78–80;
  - queue: 10 (unwraps lists) and 30;
  - command list: 7, 10, 32 (unwraps heaps), 83, 146 (→ PC 80), 148;
  - descriptor heap: 9 and 10 (return in RAX).
- **Every other slot** traps: it logs the slot and arguments once and returns `E_NOTIMPL`.
- **Inline paths:** the first 0x1000 bytes of each proxy stay zero, so the inline fast paths
  always take the vtable.
- **Not proxied:** resources, heaps, PSOs, root signatures, fences and allocators. Their
  vtables match PC as far as we know, and leaving them raw avoids unwrapping them in every call.
  Their `GetDevice` (slot 7) is patched in vkd3d-proton's shared per-class vtables to return the
  device proxy. vkd3d-proton returns one device per adapter, so every child of it is covered. The
  classes are found by creating one probe object of each; PSOs are patched on the first
  `CreateGraphics/ComputePipelineState`.

### PresentX

`shims/d3d12_xs/present.c` implements it:

- **Window and swapchain:** each queue that presents gets a window on its own message thread, and
  a flip-model DXGI swapchain (DXVK's `dxgi.dll` over vkd3d-proton) on the inner queue. The
  swapchain is recreated if the plane's size or format changes. Closing the window ends the
  process.
- **Copying the plane:** `PresentX` copies plane 0 into the back buffer on the same queue, so it
  is ordered after the title's rendering, then presents with `REBOX_VSYNC` (default 1).
- **Formats:** RGBA8, BGRA8, RGB10A2 and RGBA16F families map to swapchain formats. Any other
  plane format (e.g. R11G11B10_FLOAT) is converted into an RGBA8 intermediate with `ReboxBlit`.
  The plane goes through a shader-resource state or layout for that. HDR values are clamped.
- **Frame pacing** (`pacing.c`): a QPC clock stands in for the display's frame events. Origins
  fall every interval x period from `SetFrameIntervalX` (16.67 ms until it's called), and each
  event type sits at its `ScheduleFrameEventX` offset. A wait acts on an auto-reset event: it
  returns at once if an occurrence passed since the last wait (the newest one, so a late title
  skips frames rather than bursting), otherwise it sleeps until the next one on a
  high-resolution timer. The token is the frame number. Events passed to `ScheduleFrameEventX`
  are set by a thread. A timeout that would pass first returns `HRESULT_FROM_WIN32(ERROR_TIMEOUT)`
  (the console's code is unknown). `REBOX_FRAME_PACING=0` restores the no-ops.
  Frame dumps of such planes are BMPs of the converted image.
- **Finding the plane:** the qword at `plane_params+16` is the resource or a pointer to it.
  Both are recognised by vkd3d-proton's resource vtable. The first call logs the raw params,
  to settle the layout once a real title runs.
- **The plane's current state** comes from tracking:
  - initial states at creation (device slots 27, 29, 30, 76);
  - every barrier the title records (slots 26/15, and slot 146 by enhanced-barrier layout).

  Untracked resources are assumed COMMON.
- **Frame dumps:** `REBOX_DUMP_FRAMES` writes chosen frames as BMP. That's how the smoke test
  checks presents headless.

### Mitigations for blockers

- **Missing shader translations:** fallback shaders (see the README). XboxBvhBuilder's console
  shaders take this path too, so BVH builds become no-ops instead of failures.
- **FidelityFX:** a stub `amd_fidelityfx_loader_xbox.dll` replaces the package's (via
  `rebox-run`'s shadow package directory). Its descriptor types and dispatch offsets were
  checked against the real upscaler's exports and provider vtable. Dispatch calls `d3d12_xs`'s
  `ReboxBlit`. That compute bilinear scale is recorded into the title's list, changes its
  compute root signature and PSO as real FSR does, and restores the title's descriptor heaps,
  which list proxies now track.
- **Texture GPU VAs:** vkd3d-proton returns 0 for textures. The resource class's
  `GetGPUVirtualAddress` (slot 11, patched in its shared vtable) hands a texture scratch GPU
  memory of its allocation size. Its `Release` (slot 2) frees the scratch with the texture.
- **Audio:** XMA2 voices fail under WineGDK; `shims/xaudio2_9` plays them as silence with the
  same timing (see the README).
